# 每日文档 · 用法

## 这是什么

每个有实质工作的日子，写一份 `docs/daily/YYYY-MM-DD.md`。
**用大白话写**：今天做了什么、结论是什么、踩了什么坑、明天干嘛、要你决定什么。
专业细节留在 `research_committee/` 的报告里，这里只放「不看代码也能读懂」的部分。

## 为什么要有

项目里的五份文档（`TODO` / `DONE` / `KNOWLEDGE` / `REASONING` / `LEARNING`）是**按主题**组织的，
好处是查得到，坏处是**看不出「时间线」**——想回答「上周三我们到底改了什么、为什么改」
要翻好几个文件对日期。

每日文档补的就是这条时间线。Martin 判断进度的最快方式是**从最新一天倒着读**，
而不是从五份文档里各截一段拼起来。

## 写什么（固定五节，缺一节算没写完）

1. **今天做了什么** —— 按「用户要的 / 我顺手做的」分开列，不许混在一起讲。
2. **关键结论与数字** —— 每个数字后面跟一句判读（好 / 坏 / 中性、跟谁比）。
3. **踩的坑与怎么处理的** —— 包括**我自己的失误**。这条最重要，因为坑才是下次省时间的地方。
4. **明天做什么** —— 可执行，不写「继续推进」这种空话。
5. **需要你决定什么** —— 带推荐项；没有就写「无需决定」。

## 不写什么

- **不复制报告正文**。报告写「怎么算的」，这里写「算出来意味着什么」。
- **不写未验收的结论**。任务没验收就只登记「做了什么」，结论等验收后再写。
- **不留历史版本**。当天发现写错了，直接改当天这份（`docs/daily/` 只反映「那天最终确认的版本」）；
  结论被后来的实验推翻时，**在原处划线并注明日期与推翻它的报告**，不许静默覆盖。

## 和别的文档怎么分工

| 想知道 | 去哪里 |
|---|---|
| 某天发生了什么、为什么 | **`docs/daily/`（本目录）** |
| 接下来干嘛、卡在哪 | `TODO.md` |
| 做完了什么、有什么用 | `DONE.md` |
| 项目有什么、为什么这样设计 | `KNOWLEDGE.md` |
| 结论凭什么信、什么时候失效 | `REASONING.md` |
| 某个专业词什么意思 | `LEARNING.md`（由 `glossary/terms.yaml` 生成） |
| 这个想法测过没有、为什么停 | `research_committee/想法台账.md` |
