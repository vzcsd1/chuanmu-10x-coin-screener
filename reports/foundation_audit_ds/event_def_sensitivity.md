# 审计③ 事件定义敏感性【待验证】

> **本审计全部结论均为【待验证】**；只读原始库，不改评分、不改事件库、不覆盖 pumps.json。

## 一句话结论
原参数切出 **841** 个事件。改动「回看天数 / 涨幅门槛」后，与原集合的重合率（Jaccard）落在 **0.24~1.00**：最敏感的 `lookback=120` 只保住原事件的 **38%**，`min_gain=1.5` 只剩 **41%**。
而「启动判定 +15%」这一项，在按事件身份配对时 Jaccard=1.00——因为它**不改事件身份、只挪评估日**（见第 3 节）。

| 变体 | Jaccard(精确键, 标准) | Jaccard(宽键 symbol+trough月, 旧版) | Jaccard(评估日 symbol+pre_day) |
|---|---:|---:|---:|

- 宽键整体比精确键**高 0.03**（平均）：把同月不同事件并成一个键，会让「重合」虚高。**标准读法用精确键。**
- 评估日键是第三把尺：`ignite` 变体在精确键下 Jaccard=1.00，但在评估日键下只有 0.25——它实际挪动了 506 个事件的评估日。

## 3. 两个关键机制（判读前必须先知道）

1. **`IGNITE_MOVE` 不改事件身份，只挪「评估日」。** 它决定 `pre_day`（策略真正看着的那一天），但不动峰值、低点、涨幅。所以按精确键配对时它是「隐形」的；上表第三把尺显示它实际挪动了多少评估日。**下游区分度对启动阈值敏感，不是因为事件集合变了，而是因为「看到哪一天」变了。**
2. **`MIN_GAIN` 一参数两用，提高它不等于「在原库上过滤」。** 它既是峰值检测的门（`ret30>=MIN_GAIN`）又是事件过滤门。设 1.5 时重跑只得 351 个事件，而在原库上直接按 `gain>=1.5` 过滤有 689 条 —— **两套口径差很大**，因为门槛一动，选中的峰值日本身就变了。

## 4. 判读

- 重合率越低，说明「爆拉事件」这个地基**越依赖人为选的参数**，不是市场里的客观事实。
- 精确键下 `lookback` 与 `min_gain` 的 Jaccard 最低到 0.24；在这个量级上，下游所有区分度数字**只对该事件定义成立**，换参数要重算。
- 每个变体的完整事件清单已落盘 `event_def_variants/<变体>.json`，供 glm 逐个比对。
- 口径提示：`lookback=120` 还会触发 02 的 `n < lookback+30` 过滤，把历史长度不足 150 根的币整个排除；这部分「少掉的币」不是「少掉的事件」，两者要分开看。
