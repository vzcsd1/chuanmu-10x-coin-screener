## 两种入口不能混为一谈

实时合约筛选访问 `fapi.binance.com` 等接口，本地状态存于 `results/rate_limit_state.json`，按逻辑域与代理配置标识暂停。历史下载则直接按 `queue_v2.csv` 的 `source_url` 请求归档站，使用独立的归档状态与请求保护。

清单实读样例：`https://data.binance.vision/data/futures/um/monthly/fundingRate/ADAUSDT/ADAUSDT-fundingRate-2020-01.zip`。其中 futures/um 是文件分类，并不意味着下载请求发往实时合约 API。因此合约 API 暂停不自动阻止合约历史 ZIP 下载，前者本地暂停文件也不会被后者自动读取。不同服务仍可能共享机器/网络资源，不能说永远互不影响。

## 几小时一次的真实查询是否可靠（2026-10-07 用户追问）

不能从查询间隔保证不受限，也不能从本次记录认定只是测试轮次过多。当前单轮实际请求轨迹、服务方当时的额度与共享出口其他流量未取证。

代码证据：`binance_box_strategy.py:110` 默认扫描上限 400；`:277` 开启 CCXT 自动节流；`:677-707` 合约历史结果按小时缓存在进程内、只缓存 ok；`:710-795` 未命中缓存时逐币取持仓历史与大户持仓多空比，失败还可能请求替代口径；`:1014-1032` 对展示行另外取持仓快照和费率。正常路径若 N 个有合约的币全部进入历史计算且缓存未命中，历史部分约 2N 次方法调用，另有展示补取、市场初始化和行情请求；不是实际 HTTP 次数或权重测量。例如 N=400 时历史部分约 800 次，不能把它直接与未知的服务方额度比较。

几小时一次减少全天调用总量，却不必然减少一轮短时请求密度；跨小时缓存不再命中，重启还会失去内存缓存。自动节流已存在，但尚无证据证明它覆盖所有端点的所有限制及共享出口总流量。共享出口贡献在本事故中仅是待核实可能性。

实操影响：`:943-962` 合约信息参与评分；`:1008-1009` 按总分筛选。因此缺合约数据时继续展示现货，只是部分信息可用，可能改变排名或漏掉本应入选的币。不能把缺数据解释为该币没有潜力，也不能把降级结果作为全功能验收通过。历史 ZIP 持续下载不等于当前实时合约字段齐全。

最小验收建议（未执行）：遵守现有暂停期限，之后在用户正常查询时记录一轮请求数量/耗时、可取得的响应额度信息、合约字段完整性和数据时间，再按用户几小时一次的真实节奏观察下一轮；不为验收密集连扫。先查失败发生于初始化还是逐币取数，再决定是否需要节奏或缓存小修；不以缩小币池、取消关键字段、提高门槛或缩小盈利目标来省请求。不新增大型数据服务。若已有日志足够，优先复用。
