# 切换方法验证 · 独立假进程实验（2026-10-06）

> 目的：把"怎么安全停掉一个采集进程"从**猜测**变成**实测**。
> 起因是主代理验收指出原报告"改投 `CTRL_C_EVENT` 就能定向优雅停止"的说法不成立。
> 本轮**只做验证，不改下载器架构、不提并发、不换出口**；
> 并且**没有在真实采集进程上试过任何信号**（未验证前不试，这是本轮定下的准入条件）。

## 一、实验怎么做的

| 角色 | 文件 | 说明 |
|---|---|---|
| 假下载器 | `_fake_worker.py` | 复刻真实下载器在"被停止"上真正相关的三件事：装优雅处理器（保存 → 释放锁 → 退出）、持有活进程锁、记录收到过哪些信号 |
| 控制端 | `_probe_harness.py` | 起"目标 + 旁观"两个假进程，逐个方法发信号，记录两边的后果 |
| 外层 | `_probe_switch.py` | 把整个实验放进**新建的控制台**，本会话的控制台完全不参与 |
| 原始结果 | `switch_probe_result.json` | 每次运行的完整事件流水 |

**为什么必须另开一个控制台**：`CTRL_C_EVENT` 的作用范围就是"调用者所在的那个控制台"。
在本会话里直接发 CTRL_C，一旦范围失控会连带打到会话本身。放进新建控制台后，
最坏情况只影响实验进程。

**每个方法都同时起一个"旁观进程"**，用来回答"信号范围是否可控"——
只看目标有没有退出，是看不出误伤的。

## 二、实测结果

环境：Python 3.10.9 / Windows 10.0.22631。三次运行结果一致。

| 方法 | 目标优雅退出 | 目标锁已释放 | 旁观被误伤 | 控制端被波及 | 结论 |
|---|---|---|---|---|---|
| M1 `CTRL_C` 进程组 0 | ✅ | ✅ | ❌ **误伤** | ❌ **波及** | 范围不可控 |
| M2 `CTRL_C` 定向目标组 | ✅ | ✅ | 安全 | 安全 | **可用** |
| M2b 对照：`CTRL_C` 指向**旁观**组 | 目标没动 | — | 旁观被打 | 安全 | 证明组号真被采纳 |
| M2c 对照：`CTRL_C` 指向**不存在**的组 | 无动静 | — | 安全 | 安全 | API 返回 `False` |
| M3 `CTRL_BREAK` 定向目标组 | ✅ | ✅ | 安全 | 安全 | **可用** |
| M4 `os.kill(pid, CTRL_BREAK)` | ✅ | ✅ | 安全 | 安全 | 与 M3 等价 |
| M5 `taskkill /PID`（不带 `/F`） | ❌ 无效 | — | 安全 | 安全 | 系统回"只能强行终止这个进程" |
| M6 目标专属停止哨兵文件 | ✅ | ✅ | 安全 | 安全 | 最可控，但要目标自己轮询 |
| M7 对照：目标**没开** Ctrl+C，`CTRL_C` | ❌ **收不到** | — | 安全 | 安全 | ← 关键 |
| M8 对照：目标**没开** Ctrl+C，`CTRL_BREAK` | ✅ | ✅ | 安全 | 安全 | ← 关键 |
| M9 对照：目标**不是组长**，`CTRL_BREAK` | ✅ | ✅ | ❌ **误伤** | ❌ **波及** | ← **最危险** |
| M9b 对照：目标**不是组长**，`CTRL_C` | ✅ | ✅ | ❌ **误伤** | ❌ **波及** | ← **最危险** |

### ⚠️ 关键更正：定向失败会**退化成整控制台广播**

M9 / M9b 是事后补做的对照，**推翻了本文件初版的一个结论**：

- 初版写"`CTRL_C` 的失败模式是良性的：目标没打开 Ctrl+C 时只是**什么都没发生**"。**这是错的。**
  真正的失败模式是——**如果目标的 pid 不是合法进程组号，信号会广播给该控制台上的每一个进程**，
  包括完全无关的进程。
- 同理，**不能**用"上次 `CTRL_BREAK` 打死了旧进程"反推"它一定是进程组组长"——广播同样能打死。

**推论：投递前必须先确认目标是不是进程组组长；而这一点无法在投递前安全判定**
（`GenerateConsoleCtrlEvent` 的返回值对"合法组号"和"pid 存在但不是组号"都返回 `True`，
只有**完全不存在**的 pid 才返回 `False`，见 M2c）。

→ 因此**唯一安全的做法是先侦察控制台上还有谁**：
`_stop_graceful.py <pid> --probe`（只读，不发信号）用 `GetConsoleProcessList` 列出全部进程。
**只要控制台上还有无关进程，就不要投任何控制台信号**，改用 `taskkill /F /PID <pid>`。

### 关键发现：文档与实测为什么"都对"

微软文档说 `CTRL_C_EVENT` **不能限定到特定进程组**；我们的 M2 却定向成功了。
**两者并不矛盾**，M7/M8 这两条对照给出了解释：

- 用 `CREATE_NEW_PROCESS_GROUP` 起的子进程，**默认忽略 Ctrl+C**（这是该标志的定义行为）；
- 所以"常规情况下"往一个进程组发 `CTRL_C`，**目标收不到** → 文档的说法在常规用法下成立；
- 而我们的假下载器**显式**调了 `SetConsoleCtrlHandler(None, False)` 把 Ctrl+C 打开
  （M2/M3 那一组），于是 `CTRL_C` 就真的能定向送达；
- 对照组 M7（不打开）`CTRL_C` 收不到、M8（不打开）`CTRL_BREAK` 照样收得到。

→ **`CTRL_BREAK` 不受"有没有打开 Ctrl+C"这个前提影响，是更稳的定向手段**；
代价是目标必须自己处理 `SIGBREAK`，否则就是**直接终止**（这正是上一轮真实踩的坑）。

### 范围可控性有对照支撑，不是"看起来成功"

- M2b：把组号换成**旁观**的 pid → 旁观优雅退出、**目标毫发无损**（`rc=None` 仍在运行）。
- M2c：组号给一个不存在的值 → API **返回 `False`**，两边都没动静。
- 这两条排除了"信号其实是广播、只是恰好目标先退"的假象。

## 三、落到真实下载器上，该怎么选

真实下载器 `tools/archive_download_ds.py` **没有任何信号处理器**（全文没有 `signal` /
`SIGBREAK`），它只靠 `try/finally` 里的 `lock.release()` 兜底。因此：

| 信号 | 实际后果 | 说明 |
|---|---|---|
| `CTRL_C` | **优雅**（`KeyboardInterrupt` → `finally` 释放锁） | 前提：该进程的 Ctrl+C 是打开的 |
| `CTRL_BREAK` | **直接终止**，`finally` 不执行 → **留下孤儿锁** | 就是上一轮实际发生的情况 |
| `taskkill` 不带 `/F` | 无效 | 控制台程序收不到关闭请求 |
| 停止哨兵文件 | 需要改代码 | 本轮**未做**（不扩大架构） |

**推荐做法（下次切换时）**：先跑 `--probe` 侦察，再决定：

1. **控制台上只有目标自己** → 可以投 `CTRL_C` 到目标进程组（最好情况：优雅收尾 + 释放锁）；
   若目标没打开 Ctrl+C 则收不到，再补一发 `CTRL_BREAK`（此时广播也无害，因为台上没别人）。
2. **控制台上还有别的进程**（如本会话的 `bash.exe`）→ **不要投控制台信号**，
   直接用 `taskkill /F /PID <pid>`。数据上是安全的：
   正式文件 `.part` → `rename` **原子落盘**（不会有半个正式文件）、
   台账**每份只追加一行**且已 flush、锁有**残留接管**机制；
   代价只是当前在途的几份要重下。

**两个必须显式建立的前提**（不能靠假设）：

1. **启动采集进程时要带 `CREATE_NEW_PROCESS_GROUP`**，否则"组号 = pid"不成立，
   定向信号会**退化成广播**（M9/M9b）——不是静默丢失。
2. **发送方要与目标共用同一个控制台**（`GenerateConsoleCtrlEvent` 的硬要求）；
   跨控制台要先 `FreeConsole` + `AttachConsole`，并给自己加 `SetConsoleCtrlHandler(None, True)`
   免得误伤自己。

### 真实进程上的实例（2026-10-06 实际停止采集）

对 PID 37848 跑 `--probe`，结果：控制台上除目标外还有 **`py.exe`(31772) + 3 个 `bash.exe`**
（就是本工具会话的 shell）。进程树是 `bash → py.exe → python.exe`，
所以**组号 = 37848 不成立**（组长应是 `py.exe`）→ 投信号会广播到 3 个 bash、可能打断会话。
→ **放弃控制台信号，改用 `taskkill /F /PID 37848`**。
停止后核验：进程数 0、孤儿锁已清（先确认属主死亡）、`*.part`/`*.pending`/`*.tmp` 全 0、
台账 4,314 行 0 解析失败。**数据未受损。**

## 六、2026-10-07 更正：真实启动链下 `CTRL_C` 收不到

**本文件第三节第 1 条写"控制台上只有目标自己 → 可以投 `CTRL_C`"，对真实启动链不成立。**
2026-10-07 在真实进程（PID 23984）上实测后更正如下。

### 事实

- 先 `--probe` 侦察：目标控制台上只有**它自己的启动链**（`py.exe` + 3 个 `bash.exe`），
  并且实测**本会话自己的控制台是另一组 PID**，两者不相交 → 投递不会误伤会话。
- 投定向 `CTRL_C` 后：**进程照常跑完当前块**（11:03:50 正常出块结果），日志无任何中断记录，
  锁心跳持续刷新。**等满 4 分钟也没有反应。**

### 原因（用同构启动链做的判别实验）

| 假进程 | 是否重开 Ctrl+C | `CTRL_C` 结果 |
|---|---|---|
| `switch2` | ✅ 调了 `SetConsoleCtrlHandler(None, False)` | ✅ `handler:2 → saved → lock:released → exit:graceful` |
| `switch3` | ❌ 不重开（复刻真实下载器） | ❌ 无 handler 事件、**锁仍持有** |

→ 本机这套启动链（bash → `py -3.10` → python）**会把"忽略 Ctrl+C"标志继承给子进程**；
`py.exe`/CPython 注册的处理器**不能**覆盖它，只有显式 `SetConsoleCtrlHandler(None, False)` 才行。
真实下载器 `tools/archive_download_ds.py` 全文没有这个调用 → **`CTRL_C` 永远收不到**（与 M7 一致）。

### 更正后的结论

1. **不要**因为"控制台干净"就投 `CTRL_C`——先确认目标有没有打开 Ctrl+C，而这一点**无法在投递前从外部判定**。
2. `CTRL_BREAK` 不受该前提影响（`switch3` 收到 `handler:21` 并优雅退出，因为假进程注册了 SIGBREAK），
   但**真实代码没有 SIGBREAK 处理器** → 等于直接终止、留孤儿锁。
3. **正解是把停止入口做进代码**：2026-10-07 已实现**停止哨兵**
   （`archive_queue_ds.py stop` → 目标在块边界保存退出、释放锁、消费哨兵），
   并在真实进程上验证通过（日志 `收到停止请求（哨兵），当前块已完成，保存退出`）。
   **后续调参/维护一律走哨兵，不再投控制台信号。**
