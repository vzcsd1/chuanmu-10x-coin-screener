## 二、做了什么（代码）

改动只落在 `tools/archive_download_ds.py`、`tools/archive_queue_ds.py` 与两者测试。

| 能力 | 实现位置 | 要点 |
|---|---|---|
| **块边界换档** | `RAMP_TIERS` + `RampController` | A(8/0.02)→B(16/0.02)→C(16/0.0134)→D(32/0.01)；**只改下一块的 `Options`，不重启进程** |
| **平台期判定** | `RampController.observe()` | 上探档相对基线改善 < 10% 连续 2 窗 → **退回较低档并锁定**；资料类别变化 → 退回最低档重判；出错/被限流的块**不参与判定** |
| **档位持久化** | `ramp_v2.json` | 跨重启保持，重启后从上次档位继续（有用例） |
| **停止哨兵** | `STOP_NAME` + `stop_requested()` / `wait_with_stop()` | 块边界与暂停等待都检查；**可打断等待**；哨兵被消费后删除；**用 mtime 区分陈旧哨兵**，上次异常退出遗留的哨兵不会打死下次启动 |
| **本地退避阶梯** | `LOCAL_BACKOFF_LADDER_MS` + `take_local_backoff_ms()` | 来源没给恢复时间才用：30 分钟→1 小时→2 小时→4 小时，封顶 4 小时；**来源给了明确期限一律照办、不截短**；档位跨重启保持；有请求成功即归零 |
| **在途字节预算** | `InflightGate` | 默认 512 MiB；按 `remote_size_bytes` 预扣、读完归还；**预计就超预算的单份不跳过**，夹到上限后等空场独占跑完 |
| **请求计数** | `Downloader.requests` + `Options.last_request_count` | 唯一出口 `_get()`，**ZIP / CHECKSUM / 重试 / 恢复探测全算** |
| **每块指标** | `blocks_v2.jsonl` | 档位、workers、间隔、类别、墙钟、已确认份数/字节、请求数、失败分类、暂停、内存峰值、换档动作 |
| **停止入口** | `archive_queue_ds.py stop` / `clear-stop` | 并入现有队列工具，未新建调度平台 |

## 三、安全切换：怎么停掉旧进程

### 3.1 先核对真实身份（不用聊天里的过期 PID）

| 项 | 实测 |
|---|---|
| PID / 命令行 | `23984` ← `py.exe 27724` ← bash ← sandbox-cli；`py -3.10 tools/archive_queue_ds.py run --version v2 --chunk 5000 --interval-sec 0.02 --max-workers… --workers 4` |
| 锁 | `.archive_download.lock`，属主 23984，心跳新鲜 |
| 最新完整块 | 第 18 块（11:03:50 结束，新下 4,999） |
| 台账 | 45,767 行，**0 行解析失败** |

### 3.2 缺口：旧进程**没有**可用的优雅退出入口（实测，非猜测）

| 方法 | 实测结果 |
|---|---|
| 停止哨兵 | ❌ 旧代码没有这个入口 |
| **定向 `CTRL_C`** | ❌ **收不到**。投递后进程照常跑完第 18 块（11:03:50），日志无任何中断记录 |
| 原因（判别实验） | 用**同构启动链**（bash → `py -3.10` → python）起假进程：**重开 Ctrl+C** 的收得到（`handler:2→saved→lock:released→exit:graceful`）；**不重开**的收不到（无 handler 事件、锁仍持有）。真实下载器全文没有 `SetConsoleCtrlHandler`，所以继承来的"忽略 Ctrl+C"标志一直生效 → 与 M7 对照完全一致 |
| `CTRL_BREAK` | ⚠️ 能送达，但**真实代码没有 SIGBREAK 处理器** → 等于直接终止、`finally` 不执行、留下孤儿锁 |
| 控制台信号范围 | 先跑 `--probe` 侦察：目标控制台上只有**它自己的启动链**（`py.exe` + 3 个 `bash.exe`）；同时实测**本会话自己的控制台是另一组 PID**，两者不相交 → 不会误伤本会话 |

**结论**：首切只能用**强制终止**。它**不是"盲杀"**——数据安全性逐项验证过：正式文件 `.part` → `replace()` 原子落盘、台账每份只追加一行且已 flush、锁支持残留接管。

### 3.3 实际执行与核验

| 步骤 | 结果 |
|---|---|
| `taskkill /F /PID 23984` | 成功；启动链一并退出 |
| 停止后残留 | `*.part` / `*.pending` / `*.tmp` **全 0** |
| 台账 | 45,767 行，**0 解析失败** |
| 孤儿锁 | 属主已确认死亡后移除（**不是**删活进程锁） |
| **数据是否丢** | **没有**。停止前最后完整块完成 232,803；重启后启动扫描复用 **234,269** —— 被中断的第 19 块里**已落盘的约 1,466 份全部保留** |

### 3.4 停止哨兵在生产中验证（顺带完成）

改完 bug 需要重启时，这次用的是**新加的哨兵**而不是强杀：

```
12:19:08 INFO 收到停止请求（哨兵），当前块已完成，保存退出
12:19:08 INFO 退出：新下 9996 份 / 109699456 字节 / 20002 请求，耗时 741 秒（含暂停 0 秒）
```

核验：进程**优雅退出**、**锁已释放（无孤儿锁）**、哨兵**被消费**、PID 文件已清理。
→ 以后调参/维护都用 `py -3.10 tools/archive_queue_ds.py stop`，不再需要强杀。

- **A → B 只快 3.9% / 4.0%**，两窗都不足 10% → 平台期 → `revert B→A`，`locked=true`。
- **瓶颈不在并发数**：8 路 ≈ 16 路。8 路时约 **30.4 请求/秒**，远低于该档 50 请求/秒的节奏上限；16 路也没有把间隔用满。按任务书第 2 节，**"主要等待转成带宽/代理"时保留较低档**。

### 4.2 含等待时间的累计吞吐（任务书第 5 节要求）

本轮实测窗口内有**两段传输层卡顿**，正好说明"不能拿最快一阵当整体速度"：

| 块 | 档位 | 墙钟 | 份/秒 | 失败 |
|---|---|---:|---:|---:|
| 1 | A | 981s | 4.88 | 203 × ProxyError |
| 2 | A | 1,728s | 2.60 | 492 × ProxyError |
| 3 | A | 328s | 15.22 | 0 |
| 4 | B | 316s | 15.82 | 0 |
| 5 | B | 316s | 15.82 | 0 |

- **累计**：24,280 份 / 3,729 秒 = **6.51 份/秒**（含卡顿）
- **干净窗口**：15.2–15.8 份/秒
- **本轮限流暂停 0 次、暂停 0 秒**（所以"含暂停的累计"就是上面的累计墙钟口径）

> 若按任务书的例子换算：15.8 份/秒 跑 5 分钟、再卡 30 分钟，总平均会掉到约 3.9 份/秒——**低于旧 4 路的 11.65**。所以"高速一阵"只有在总完成时间更短时才保留。

## 五、本轮修掉的三个真缺陷

| # | 缺陷 | 影响 | 修法 |
|---|---|---|---|
| 1 | **`paused_block = "限流暂停" in summary`** | 汇总串里**永远**含字面量「限流暂停 0」→ **每一块都被判成"被限流"** → 逐档永远拿不到干净样本（第 2 块仍停在 A）。同一处也让旧代码的 `no_progress` 兜底**彻底失效** | 改为按**实际结果状态** `any(r["status"] == S_PAUSED)`；已加回归 `test_summary_wording_does_not_fake_a_pause`（还原错误写法时该用例失败） |
| 2 | 块耗时用 `time.time()` 测量 | Windows 分辨率约 15 ms，块耗时可能为 0 → 判定成"无有效吞吐" | 改用 `time.perf_counter()` |
| 3 | `process_rss_bytes()` 恒返回 0 | 内存峰值采不到 | `GetCurrentProcess()` 返回伪句柄 (-1)，不声明 `argtypes` 会被截断成 32 位；已显式声明（实测 20.6 MB） |

> 缺陷 1、3 的修复**对当前运行的进程尚未生效**（模块已加载）；下次重启生效。不影响数据正确性。

## 六、未解决 / 环境问题（不掩盖）

1. **阵发性 ProxyError（主要瓶颈）**
   - 本轮共 695 次 `failed_transient`，原因**全部是** `ProxyError ... data.binance.vision`。
   - **不是限流**：暂停表为空、无 429/418。**数据没丢**：这些条目在后续块被重试并成功，台账里现在为 0。
   - 只读并发对照（8 并发 × 320 请求 × 两条链路）：**640/640 成功**，22–30 请求/秒 → 说明链路是好的，故障是**时间上成簇**的。
   - **代价是时间**，不是正确性。

2. **出口没有更换（按任务书要求）**
   - 实测对外 IP：经 sandbox 代理 `127.0.0.1:3725` → `223.104.x`（中国移动，**与直连同 IP**）；经机场 `127.0.0.1:7897` → `<egress-ip>`（**境外，换出口**）。
   - 任务书明确"**不得用换 IP/出口绕过已知暂停**"，且当前**并无暂停**，所以**没有切到 7897**，保持原出口。

3. **内存峰值未采到**（本进程仍带缺陷 3 的旧代码）；已在代码层修好，下次重启即生效。

4. **C / D 档未实测**：逐档在 B 档就判出平台期并锁定，按任务书"最多到 D、不硬试"，没有为了凑数据继续加线程。
