## 3. 已取证的检查起点（不是已确定根因）

| 位置 | 当前事实 | 需要验证的影响 |
|---|---|---|
| `ui/static/ocean.js::measureFPS` | 独立 requestAnimationFrame 回调间隔；不统计两个画布的实际提交次数 | 约 60 的读数不能证明每层都在约 60 次更新，也不能单独证明用户看到的流畅度 |
| `ui/static/result-fx.js::loop/draw` | 至少隔 40ms 才画一次；在主线程逐像素计算正弦并 putImageData | 画布更新节奏、主线程占用是否让水光步进或挤占海面；60Hz 下该节流还可能量化到约 50ms，须实际测量 |
| `result-fx.js::draw/resize` | 慢帧触发一次降分辨率，但 resize 又按初始规则计算尺寸，degraded 标记未恢复 | 开合/窗口变化是否撤销已降画质且不再调整；不凭源码就宣称已复现 |
| `ocean.js::drawFrame` | 初期约 150 帧检查后可置 perfChecked=true，后续结果态不再持续评估 | 首页正常后新增结果负载是否错过调整机会 |
| `result-fx.css` + `style.css` | 大面板透明/模糊/混合，多卡片持续 CSS 动画；折叠保留 grid 结构 | 长列表、滚动、收起、后台与静态模式是否仍有不必要的绘制/布局 |
| `result-fx.js` | 卡片 pointermove 逐事件读布局并写样式；观察器主要管入场 | 高频移动和屏外卡片成本是否可见，静态按钮是否真正停止相关工作 |

K3 的报告记录 100 卡滚动最差单帧折算约 11.9 FPS；不能把它当持续帧率，也不能由一次平均值断言“没有性能退化”。用户已反馈卡顿，本次性能项未通过。原始报告与录屏保留，不覆盖。

## 4. 实施顺序

1. **先保存可比基线。** 核对当前文件摘要、浏览器版本、窗口尺寸、缩放/像素比、可取得的图形加速信息。复现首页看海、5 卡结果、100 卡滚动、详情快速开合、整批收起再展开。首先尽量匹配用户实际桌面浏览器，不能仅以无窗口浏览器结果证明桌面流畅；无法取得同环境时明确限制。
2. **区分哪一层慢。** 在演示测试里依次暂时关闭新增水光层、卡片装饰、面板模糊、海面，作短时间对比定位；这些只用于诊断，最终恢复必要视觉。记录浏览器回调间隔、海面实际绘制次数、水光实际绘制次数；能取得时记录主线程长任务及绘制/合成开销。JS 提交绘制也不等于实际呈现，最终同时看实际画面。
3. **按证据作最小修复。** 优先消除不必要的计算、巨大离屏图层、重复读写布局与后台工作；对实际负载持续调整分辨率/细节，避免频繁升降与尺寸变化抵消降档。动画按真实经过时间推进，平衡画质和连续性；不是简单把所有层限到低帧率。允许替换确实过重的水光计算实现，先在已有工具内解决，禁止每卡新建渲染器/线程/循环。
4. **保持暂停与可见性完整。** 背景标签、屏外、结果隐藏、整批收起和动态关闭时停止对应持续工作；回到前台正常恢复，不补播积压帧，不卡住转场 Promise。减少动态偏好仍受支持，用户选择静态时功能完整。
5. **同条件验证再交付。** 用同一演示数据、窗口、浏览器、操作顺序做前后对比；不能通过少卡片、缩小窗口、静止不滚动或删特效来粉饰结果。修复后确认过滤、复制、详情、整批收起/展开、状态轮询不重播、旧结果与缺数据文案仍正确。

允许编辑 `ui/static/ocean.js`、`result-fx.js`、`result-fx.css`，以及确有必要的 `style.css`、`index.html`、`app.js` 视觉接线；不得改变网络请求/轮询语义、扫描流程或默认自动查询。必要的隔离夹具/测试可新增在测试专用位置。禁止修改后端、生产策略、研究数据与 B4 冻结文件。公共 TODO/DONE/KNOWLEDGE 由主代理维护，不自行提交或推送。
