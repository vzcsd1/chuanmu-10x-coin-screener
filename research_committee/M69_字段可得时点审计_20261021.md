## 1. 问题是什么：前视偏差比「指标不好用」严重一个量级

如果某个字段是**事后补的**，那我们所有用它算出来的结论都用了「当时看不到的信息」。
这不是「这个指标没用」，而是**整个结论作废**。所以它是 92 机制里最便宜的地基（2 小时）。

三个必须分开回答的问题：

| # | 问什么 | 怎么测 |
|---|---|---|
| ① | 归档里 day D 的文件，什么时候才出现？ | HTTP HEAD 的 `Last-Modified`（真实发布时刻） |
| ② | 实盘 API 的 5 分钟桶，当时能不能拿到？会不会被改写？ | 直连 `fapi`，同一桶隔 75 秒取两次比对 |
| ③ | 我们算特征时，实际用的是哪一刻的值？ | 逐文件检查行序与取值时点 |

> 注：本机 `fapi.binance.com` 直连不通（返回 000），实测走系统代理 `127.0.0.1:7897`。
> 这是**本机网络问题，不是币安限制**——实盘程序本来就走代理。

## 2. ① 归档发布延迟：全部 T+1，最晚约 34 小时

`Last-Modified` 实测（UTC，2026-10-21 采样）：

| 数据集 | 数据日 | 发布时刻 | 距当日 00:00 |
|---|---|---|---:|
| **metrics 日度**（OI / 多空比 / taker） | 10-14 | 10-15 06:50 | 30.8h |
| | 10-15 | 10-16 07:13 | 31.2h |
| | 10-16 | 10-17 06:41 | 30.7h |
| | 10-17 | 10-18 06:37 | 30.6h |
| | 10-18 | 10-19 07:39 | 31.7h |
| | 10-19 | 10-20 06:37 | 30.6h |
| | 10-20 | 10-21 06:46 | 30.8h |
| **K线 1d / 1h 日度** | 10-14 ~ 10-19 | D+1 07:57–09:43 | **32.0–33.7h** |
| | 10-20 | **10-21 10:15 仍 404** | 未发布 |
| **fundingRate 月度** | 2026-08 / 09 | M+1 08:24 / 08:47 | 32.4 / 32.8h |
| **K线 1h 月度** | 2026-08 / 09 | M+2 09:48 / 09:36 | **57.8 / 57.6h** |

**读法**：归档是「隔天早上才给你」的。所以**任何「当天收盘就用当天数据」的研究都是前视**。
本项目的研究脚本用的是**前一日及更早**的日文件，加上当日 ≤23:00 的 K 线，
所以只要不碰「当日全天汇总」，就不构成前视。

**两个要记住的细节**：
- **日度 K 线的发布比 metrics 不稳定**：10-20 的 K 线在 10-21 10:15 UTC 还是 404，
  而同日 metrics 已在 06:46 发布。**依赖日度 K 线归档做增量更新时会踩空**，要有重试。
- **月度 K 线是 M+2**（两个月后才齐），所以「月度 K 线」不能用于近月研究。

## 4. ③ 我们自己取的是哪一刻：一个只在 2026-08 之后出现的坑

### 4.1 代码现状

`05_deriv_features.py:86` 取的是 `df["sum_open_interest_value"].dropna().iloc[-1]`——
**「文件里的最后一行」**，而不是「时间最晚的那一行」。这在文件按时间排序时等价，
在文件乱序时就是**随机时刻的快照**。

### 4.2 实测：行序从 2026-08 起被打乱

| 数据日 | 288 行 | 是否按时间递增 | 末行时刻 |
|---|---|---:|:---|
| 2022-06-15 ~ **2026-07-15** | 288 | **是** | 23:55 ✅ |
| 2026-08-15 | 288 | **否** | 23:35 |
| 2026-09-01 | 288 | 否 | 23:50 |
| 2026-09-15 | 288 | 否 | 23:40 |
| 2026-10-01 | 288 | 否 | **22:15** |
| 2026-10-15 | 288 | 否 | 23:40 |
| 2026-10-20 | 288 | 否 | 23:45 |

**边界在 2026-07-15 与 2026-08-15 之间。** 乱序程度是「行位置与时刻的 Spearman 仅 0.08」，
即基本随机——但末行恰好落在 23:xx 的概率仍有 95.6%（1,444 个「币-日」实测），
所以**大部分情况碰巧没出错**。

### 4.3 影响有多大

| 对比 | 中位 | p90 | 最大 |
|---|---:|---:|---:|
| 末行 vs 真 23:55 的 OI 偏差 | 0.00% | 0.00% | **67.8%** |
| 23:55 vs 决策安全 22:55 的 OI 偏差 | **0.53%** | 1.85% | 12.8% |

**两个不同性质的问题，别混在一起**：
- **行序坑**（末行 vs 23:55）：只影响 2026-08 之后的数据，最大 67.8%，是**测量错误**；
- **前视坑**（23:55 vs 22:55）：影响全部历史，中位 0.53%，是**信息泄漏**。

## 5. ④ 前视到底改不改结论：不改

用 `features_deriv.csv` 的样本重算 `oi_chg_1d` 三种口径（397 条可用，其中爆拉 164 条）：

| 口径 | 覆盖 | AUC | 上下 1/5 分位爆拉率差 | 与现状的秩相关 |
|---|---:|---:|---:|---:|
| ① 现状：文件顺序末行（有 bug） | 100% | **0.604** | 23.75pp | 1.000 |
| ② 修正排序取真末行 23:55（前视 55 分） | 100% | 0.608 | 25.00pp | **0.989** |
| ③ 决策安全 22:55（无前视） | 100% | **0.603** | **27.50pp** | 0.960 |

**判定**：
- 安全口径与现状口径的秩相关 **0.960**，AUC 差 **−0.001**——**是同一个变量**。
- 更值得注意的是：**安全口径的分位差反而更大**（27.50pp vs 23.75pp）。
  如果前视在「注水」，安全版应该变差；它没有。**说明 55 分钟的 OI 变化里没有可利用的信息。**
- 所以：**历史结论不因这个 55 分钟而作废**，`oi_chg_1d` 的「AUC ≈ 0.60、分位差 20+pp」
  这个量级是真实的。

## 7. 我可能错在哪

1. **`impact` 只有 397 条可用**（`features_deriv.csv` 733 条里，前后两天都能对上 metrics 的只有 397）。
   AUC 的 95% 带约 ±0.05，所以「0.604 vs 0.603」这个**差 0.001 的结论是稳的**
   （两个口径是同一个样本上的配对比较，相关 0.96，配对误差远小于 0.05）；
   但「AUC 到底是 0.60 还是 0.65」这种绝对水平，397 条不够精确。
2. **实盘只测了一次、一个币（BTCUSDT）**。taker 多 5 分钟这个结论只有一次观测，
   可能是偶发。**要用 3 个币 × 3 个时点复测才能定论**（TODO 已记）。
3. **归档发布时刻只测了最近 7 天 + 2 个月**。更早的时期可能不同（比如 2022 年是否也 T+1 未验证）。
   这不影响结论（研究用的是「隔天以后才跑」），但**如果要做「当天收盘就出信号」的实盘，必须重测**。
